# Страницы настроек и кнопки действий

Как сделать у нас страницы «как в приложении» и не привязаться к одной модели. Сверено с приложением на r2505 (дамп `dreame-app/plugin-research/tools/mkdump.py`, 2026-11-25).

## Что устроено сейчас
- Каталог настроек `agent/ui/settings.js`: `siid/piid`, вид (`bool`, `select`, `number`, …), способ достать значение из упакованного свойства (`bit`, `auto`, `json_key`, `packed`), `hw` (что должна подтвердить таблица прошивки), `advanced`, `confirm` (спросить перед включением).
- Строка настройки показывается, только если робот ответил на свойство (`decodeSetting`) и `hw` не против. Для другой модели ничего не нужно переписывать: что робот не знает, того в интерфейсе нет.
- Группы (`settingGroups` в `app.js`) повторяют страницы приложения: «Чистка пола», «MopExtend и боковой вылет», «Ножки: преодоление препятствий», «Ковры», «Препятствия и ИИ», «Базовая станция», «Голос»…

## Как сделать страницы целиком
1. **Страница = данные.** В `settings.js` рядом с настройками появляется список страниц `pages: [{id, title, items:[id…]}]`. Порядок и названия берутся из плагина модели (`tools/import_plugin_spec.py` уже достаёт его свойства). Вместо правил по `id` каждая настройка получает страницу явно; правила остаются запасным вариантом.
2. **Страница видна, если видна хотя бы одна её строка.** Так у модели без боковой щётки или без станции нужных страниц просто нет, а у новой модели появляются страницы, чьи свойства она ответила.
3. **Новая модель = новый список из её плагина.** Импортёр запускается для набора плагинов (`MODELS`), записи объединяются; `src` показывает источник. Проверка по `hw` (таблица прошивки `dconf_runtime.json`) закрывает то, что прошивка отвечает, но железа нет.
4. **Перед записью — те же защиты:** `expected` (старое значение), блокировка при другой команде, `confirm` для включений, которые что-то ухудшают.

## Кнопки действий
Действия нужны там, где в приложении кнопка вместо тумблера (мойка швабр, выгрузка пыли, сушка, возврат на базу, ярлыки).
1. **Каталог действий** `actions.js`: `{id, label, page, siid, aiid, in, confirm, danger, needs}`. `needs` — те же `hw`-условия и признак «станция есть».
2. **Показ.** Кнопка видна, если действие есть в спецификации модели и нужные условия выполнены; на странице она стоит рядом с настройками, к которым относится.
3. **Отправка** только через разрешённый список агента (`local.command` по имени), а не произвольный `action`: имя → фиксированные `siid/aiid/in`. Опасные (`danger`) просят подтверждение и блокируются, пока идёт уборка.
4. **Состояние.** Пока команда выполняется, кнопки страницы выключены, как сейчас у станции; результат читается из свойства, а не из ответа на вызов.
Станционные команды (`empty`, `wash_mop` и др.) у нас уже сделаны так; остальные переводятся на каталог по одной.

## Камера в реальном времени
В приложении это облачная функция: «Включить» запускает на роботе режим задания кода доступа (действие `10001/4`, свойство `1104` = 1, опрос `10001.1103`), после чего нужно три раза нажать кнопку станции и задать код; выход из экрана отправляет `1104` = 0. Без этого физического шага и кода включить нельзя, поэтому у нас остаются поездки и патруль. Живой поток в облаке с нашей стороны не воспроизвести.
