# Dreame Local Agent

Локальный агент для робота Dreame X50 Pioneer Edition (R2505) с root-доступом. Версия **0.8.0**: к исходникам 0.5.0 из `dreame-local.zip` добавлены слой модели устройства, `/api/v1`, устанавливаемые модули и обновление агента из веб-интерфейса.

Агент написан на Go, работает **на самом пылесосе**, вызывает штатный `avacmd` и предоставляет HTTP API и встроенный веб-интерфейс. Отдельный мост на Raspberry Pi для работы агента не требуется.

## Возможности

- Состояние робота, управление уборкой, зарядкой и станцией через локальный HTTP API.
- Веб-интерфейс с выбором комнат и сохранённой картой, редактирование комнат и настроек.
- Настройка Wi-Fi и captive portal в режиме точки доступа.
- Модули, которые ставятся из веб-интерфейса (см. ниже). Региональная защита — отдельный модуль в своём репозитории.
- Проверка ожидаемых model/DID/MAC и Bearer-токена; без облачного API в рабочем режиме.

Сохранённая карта доступна локально; **живое положение робота и маршрут пока не реализованы**. Часть команд станции, Wi-Fi и редактирования карты проверялась на тестовом стенде, но не на всех прошивках и состояниях устройства.

## API для адаптеров (`/api/v1`)

Все запросы с заголовком `Authorization: Bearer <token>`, ответ `{"result": ...}` или `{"error": ...}`.

- `GET /api/v1/state` — кэш состояния. Агент сам опрашивает робот раз в 5 с и сразу после команды, клиенты робот не нагружают. Поля: `activity` (`cleaning|paused|returning|docked|idle|error`), `status`/`status_name`, `battery`, `charging`, `suction`, `water`, `station`, `volume`, `error`, `region`, `region_code`. Свойства, на которые робот не ответил, отсутствуют. `stale: true` — последний опрос не удался, `seq` растёт при каждом изменении.
- `GET /api/v1/capabilities` — модель и прошивка, совпадение прошивки с проверенным профилем (`firmware.verified`), аппаратная таблица модели из самой прошивки (`/ava/conf/dconf_runtime.json`), читаемые свойства и доступность команд.
- `POST /api/v1/command` — `{"name": "start|pause|stop|dock|locate|mapping|empty|wash_mop|dry_start|dry_stop"}`, `{"name": "set_suction|set_volume", "value": N}`, `{"name": "clean_rooms", "rooms": [ids], "repeats": 1..3, "suction": 0..3, "water": 1..3}`. Те же правила, что у `/rpc`: нужен `allow_control`, поддерживается `X-Dreame-Request-ID`, ненулевой код робота возвращается ошибкой. Команда блокируется, только если аппаратная таблица явно говорит, что узла нет.

- `GET /api/v1/events` — тот же снимок потоком Server-Sent Events: сразу текущий, затем при каждом изменении (`id: <seq>`, `event: state`, `data: <снимок>`), комментарий-пинг раз в 20 с. Не больше 8 потоков одновременно.

`/rpc` остаётся без изменений для веб-интерфейса и отладки.

### Токены с правами

Основной `token` из конфигурации даёт полный доступ. Для умного дома и других устройств создай отдельный токен в веб-интерфейсе («Доступ») или через `POST /api/v1/system/tokens` `{"name": "ha", "scope": "read|control"}`. Токен показывается один раз; в конфигурации хранится только его SHA-256. Список — `GET /api/v1/system/tokens`, отзыв — `DELETE /api/v1/system/tokens/<name>`; управлять токенами может только основной токен.

| Права | Доступно |
|---|---|
| `read` | `GET state`, `capabilities`, `events`; чтение через `/rpc` (свойства, карта, статус сети) |
| `control` | то же и `POST /api/v1/command` |
| основной токен | всё, включая модули, обновление агента, настройки, Wi-Fi, перезагрузку и запись через `/rpc` |

## Модули

Модуль — пакет `.tar.gz`, который ставится в веб-интерфейсе: «Модули» → «Установить модуль» → «Проверить пакет» → «Установить». Перед установкой панель показывает манифест, файлы и SHA-256 пакета. Подписей нет: модуль работает на роботе с правами root, ставь только из источника, которому доверяешь. Установка и удаление требуют `allow_control`.

Пакет распаковывается в `/data/dreame-local/modules/<name>/`. Содержимое:

- `manifest.json` — `name` (`a-z0-9_-`), `version`, `title`, необязательные `description`, `handler`, `panel`, `read_actions`, `firmware_messages`;
- `handler` — исполняемый файл (shell-скрипт или бинарник). Агент запускает `handler <действие>`: параметры JSON приходят в stdin, скалярные — ещё и в переменных `P_<ключ>`; ответ — JSON в stdout, ошибка — ненулевой код и `{"error": "..."}`. Окружение: `DREAME_MODULE_DIR`, `DREAME_API`, `DREAME_MODULE_TOKEN`. Действия жизненного цикла: `check` (до установки, отказ отменяет её), `install` (после копирования, при ошибке возвращается прежняя версия), `uninstall` (перед удалением). Остальные действия вызываются как `POST /api/v1/m/<name>/<действие>`; без `allow_control` доступны только `read_actions`;
- `panel` — ES-модуль `export default function mount(element, ctx)`: `ctx.read/ctx.call(действие, параметры)`, `ctx.rpc(метод, параметры)`, `ctx.onState(fn)`, `ctx.toast(текст, ошибка)`;
- `boot-env.sh` — подключается из хука загрузки робота до старта `ava` (например, чтобы предзагрузить библиотеку). Не должен завершать оболочку; действует после перезагрузки.

Токен модуля (`DREAME_MODULE_TOKEN`) даёт только `GET /api/v1/state`, `capabilities`, `events` и `POST /api/v1/firmware_message` — `avacmd msg_cvt` с `cmd` из `firmware_messages` манифеста и не более 7 скалярными полями. Ответа прошивки у этих сообщений нет: результат — «отправлено», а не «применено».

API: `GET /api/v1/modules`, `POST /api/v1/modules/stage` (тело — пакет), `POST /api/v1/modules/install` (`{"id"}`), `POST /api/v1/modules/remove` (`{"name"}`).

## Обновление агента

Новая версия ставится в веб-интерфейсе: «Обновление агента» → выбрать файл → «Проверить файл» → «Обновить». ADB для этого не нужен, только первая установка (см. ниже).

- Агент принимает только исполняемый файл Linux под архитектуру робота, который отвечает на `--version` строкой `dreame-local-agent <версия>`.
- Замену делает отдельный процесс-помощник (тот же бинарник с `--apply-update`): останавливает агент, ставит новый файл, прежний сохраняет как `dreame-local-agent.previous` и ждёт до 45 с, пока новая версия ответит своей версией на `/api/v1/capabilities`. Если не ответила — возвращает прежнюю, а новую откладывает в `dreame-local-agent.failed`. Резервная копия для ручного отката при этом сохраняется.
- «Вернуть версию …» ставит `dreame-local-agent.previous` тем же способом.
- Обновляются только бинарник и встроенный в него веб-интерфейс; `start.sh`, `stop.sh`, `boot-env.sh` и хук загрузки остаются прежними.

API (нужен `allow_control`): `GET /api/v1/system/update`, `POST /api/v1/system/update/stage` (тело — файл), `POST /api/v1/system/update/apply` (`{"source": "staged" | "previous"}`). Результат последнего обновления — в `/data/dreame-local/update-result.json`.

Версию сборки задаёт `-ldflags "-X main.version=..."`.

## Сборка

Нужен Go 1.24 или новее. Для целевого устройства требуется Linux ARM64:

```sh
cd agent
go test ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -buildvcs=false -ldflags='-s -w -buildid=' -o dreame-local-agent-linux-arm64 .
```

## Установка

Создай `bridge/config.json` на основе `bridge/config.example.json`; задай случайный `token` длиной не менее 32 символов и значения `expected_model`, `expected_did`, `expected_mac`, соответствующие твоему устройству. **Не публикуй этот файл**.

После сборки агента (см. выше), имея ADB с root:

```sh
python3 tools/install_agent.py --serial ROBOT_IP:4567 --config bridge/config.json
```

Установщик проверяет root, ARM64 и идентичность устройства, затем развёртывает агент в `/data/dreame-local`, проверяет SHA-256 и HTTP-ответ. При обычном режиме добавляет в существующий `/data/test/ava.sh` запуск агента и подключение `boot-env.sh` модулей, сохраняя резервную копию. Обновление прошивки переименовывает `ava.sh` в `ava.sh_ok`: после него агент и модули не запускаются, пока хук не восстановлен. Для ручного запуска без изменения boot hook используй `--no-boot-hook`.

Веб-интерфейс после запуска: `http://ROBOT_IP:8765/`.
Не открывай порт 8765 в интернет: интерфейс предназначен для доверенной LAN.

## Тесты

Контракт ошибок операций карты и разрешения для map request описаны в [docs/map-results.md](docs/map-results.md). Для карты одного внешнего code0 недостаточно: проверяется отдельный operation result, а неизвестный исход не повторяется автоматически.

```sh
cd agent && go test ./... && go vet ./...
cd .. && python3 -m unittest discover -s tests -p 'test_install_hook.py' -v
# Дополнительные UI-тесты используют Playwright:
node tests/test_command_results.cjs
node tests/test_web_ui.cjs
```

Go-тесты рассчитаны на Linux (`Setsid`, mock `avacmd` на Python). На Windows собери тестовый бинарник и запусти его в WSL:

```sh
cd agent && GOOS=linux GOARCH=amd64 go test -c -o agent.test . && wsl ./agent.test
```

## Состав

- `agent/` — Go-сервис, встроенный веб-интерфейс и shell-скрипты.
- `tools/install_agent.py` — установка через ADB, с проверками идентичности.
- `tools/configure.py` — подготовка конфигурации из локального диагностического отчёта.
- `tests/` — тесты веб-интерфейса и установщика.
- `bridge/config.example.json` — **только шаблон**, без личных данных и токенов.
- `custom_components/dreame_local/` — минимальная интеграция Home Assistant поверх `/api/v1`: штатная сущность `vacuum` (старт, пауза, стоп, на базу, найти, мощность) и сенсор батареи. Скопируй папку в `config/custom_components/`, перезапусти HA и добавь «Dreame Local» с IP, портом и токеном агента. Агент должен слушать LAN (`bind`), а для команд нужен `allow_control`.

Это репозиторий **исходников агента**, а не полного пакета `dreame-local`: внешний Python-мост и диагностические данные сюда не включены. Сведения об атрибуции находятся в `NOTICE.md` и файлах лицензий.
